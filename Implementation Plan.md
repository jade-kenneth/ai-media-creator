### Deferred-dependency QA

- A temporary QA stand-in (seeded fixture, stubbed resolver, fake handler) is allowed **only when the backend data or integration a row needs does not exist yet**. If the real operation, seed or integration exists, QA runs against it; substituting a stand-in for an existing dependency is an automatic row failure.
- With the stand-in in place, run every row now. Visual rows pass or fail on their own merits and are never deferred.
- Any row whose verification touched a stand-in is marked `🔁 re-verify (Phase N)` naming the phase that delivers the real dependency. A `🔁` row is not a pass.
- Every stand-in carries a `QA-BYPASS(Phase N)` marker comment — including files under `qa-fixtures/` — and never ships beyond QA.
- The screen stays `[~]` while any `🔁` row remains. When the blocking phase completes, remove the stand-in, confirm zero `QA-BYPASS` hits and zero `qa-fixtures/` references for that screen, and re-run exactly the `🔁` rows. “No prototype runtime leakage” is always in the re-verify set when a stand-in was used.
